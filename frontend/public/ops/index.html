1. 两个项目的定位

两个目录是两个独立项目，各自有自己的 .venv、uv.lock 和 Git 仓库。它们之间只通过网络（Kafka、HTTP、WebSocket）以及一处 Python 导入相连。

项目路径负责什么运行方式Git
K knetsentinel~/knetsentinel用 KVM 起 5 台 VM 组成 K8s 集群；Cilium/Hubble 观测流量 → Vector → Kafka；发正常 / 攻击流量；采数据集；端到端评估shell 脚本 + uv run / sudo .venv/bin/python3 手动运行只跟踪 README、pyproject、uv.lock、requirements.txt，脚本和清单不在 Git 中
N NetSentinel~/github/NetSentinelDjango 5 后端（kcore 集群管理 / autotf Terraform 扫描 / vigil 流量检测）+ Vue 3 前端 + 集群内检测器镜像systemd user 服务 netsentinel（uvicorn :8080）+ Docker 容器 pg + cloudflared 隧道全量跟踪，main 分支

2. 检测数据链路（三条入口）

流量最终都写进 PostgreSQL 表 vigil_detectionrecord，但有三条入口。当前实际在运行的是入口 A（后端日志中持续有 vigil.bridge: queue: N flows → M attack(s)）。

数据包 → Cilium eBPF → Hubble Relay :4245 → Vector DaemonSet → Kafka topic ebpf-net-logs
                                                                   │
        ┌──────────────────────────────────────────────────────────┼──────────────────────────────┐
        ▼ 入口 A（默认，随后端自动启动）                           ▼ 入口 B（集群内 Pod）          ▼ 入口 C（宿主机脚本）
  N backend/vigil/bridge.py                               N detector/detector.py            K kafka/vigil_bridge.py
  Kafka 外部地址 .200-.203:9094                           镜像 soar009/netsentinel-detector  按 5 元组聚合 30 特征
  group=vigil-bridge, offset=latest                        group=vigil-detector               POST /api/vigil/detect/batch/
  线程内聚合 → flow_queue → drainer 线程                   Pod 内自己推理                     (JWT)
  → services.detect_batch()                                → WS ws/detector/push/
        │                                                   (Bearer VIGIL_BRIDGE_TOKEN)
        └───────────────► ads_ml OCSVM 推理 → Cilium 策略(stub) → INSERT vigil_detectionrecord ◄──────┘
                                                                   │
                                     前端 /vigil、/vigil/log 轮询 REST 接口读取（每 15 秒）
不要同时开两条以上入口：A、B、C 各自独立消费 Kafka 并写库，同一条流会被重复记录。入口 A 无开关，只要后端以 uvicorn 启动就会运行（判断逻辑见 vigil/apps.py 的 _should_start_bridge()）。

离线评估另有一条旁路：K simulation/simulate_4.py 直接 django.setup() 导入 N backend 的 vigil.services，把 CSV 中的流特征批量送入模型。这是两个项目之间唯一的代码级耦合，路径写死为 ../../github/NetSentinel/backend。

7. 跨项目契约（改一端必须查另一端）

契约knetsentinel 侧NetSentinel 侧改动时注意
Kafka topic 名与地址cilium-vector/vector-5nodes.yaml（sink topic）、.envvigil/bridge.py 常量 KAFKA_BOOTSTRAP、KAFKA_TOPIC（写死）；detector.py 环境变量MetalLB 分配的 .200-.203 若变化，入口 A 必须改代码并重启
Hubble 流事件 JSON 结构Vector exec hubble observe --output=jsonbridge.py 读取 flow.IP / l4 / traffic_direction / verdict / is_reply / time升级 Hubble 版本后需验证字段
35 个流特征dataset/aggregate_flows.py、kafka/vigil_bridge.py、docs/features.mdvigil/serializers.py FlowInputSerializer、ml/models/base.py DetectionInput、runner.py flow_from_dict、bridge.py compute_flow五处必须同名同义；见 特征表
标签规则攻击源 .20-.29 → 1、正常源 .50-.64 → 0bridge.py _hubble_to_packet() 同样规则simulation/ 用的 .170-.184 不在规则内，label 为空
检测器推送Secret detector-secret（key django-token）→ 环境变量 DJANGO_TOKENDetectorPushConsumer._auth() 与 settings.VIGIL_BRIDGE_TOKEN 做字符串全等比较两边必须是同一个字符串；不是校验 JWT 签名
REST 批量检测kafka/vigil_bridge.py --token <JWT>POST /api/vigil/detect/batch/JWT access 默认 2 小时过期；长期运行用 generate_bridge_token 生成 10 年 token
评估监听 WebSocketsimulation/monitor/monitor.py 连接 ws://localhost:8080/ws/vigil/后端没有这个路由（只有 ws/detector/push/ 和 Pod 日志）monitor 目前连不上；需在 vigil/routing.py 补广播 consumer 或改 monitor 轮询 REST
离线导入simulation/simulate_4.pyvigil.services.detect_batch(flows, model_name)移动目录或改函数签名都会破坏
模型文件—backend/vigil/ml/ads_ml/ → detector/build.sh rsync 到 detector/ads_ml/改模型后入口 A 重启后端，入口 B 重新 build + rollout
