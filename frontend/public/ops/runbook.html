4. 开机恢复（宿主机重启后）

确认自动恢复的部分
systemctl --user is-active netsentinel cloudflared-knettf
docker ps --filter name=pg --format '{{.Names}} {{.Status}}'
virsh -c qemu:///system net-list --all | grep virbr-k8s
sysctl net.ipv4.ip_forward
预期：active active；pg Up；virbr-k8s active yes；ip_forward = 1。
后端这时已启动，但集群还没起来，bridge 线程会因连不上 Kafka 退出，第 8 步会重启后端。
恢复 VM 出网的 iptables 规则
sudo iptables -t nat -C POSTROUTING -s 192.168.100.0/24 ! -d 192.168.100.0/24 -o enp6s0 -j MASQUERADE 2>/dev/null \
  || sudo iptables -t nat -A POSTROUTING -s 192.168.100.0/24 ! -d 192.168.100.0/24 -o enp6s0 -j MASQUERADE
sudo iptables -C FORWARD -s 192.168.100.0/24 -j ACCEPT 2>/dev/null || sudo iptables -A FORWARD -s 192.168.100.0/24 -j ACCEPT
sudo iptables -C FORWARD -d 192.168.100.0/24 -j ACCEPT 2>/dev/null || sudo iptables -A FORWARD -d 192.168.100.0/24 -j ACCEPT
命令幂等，可以重复执行。出口网卡若不是 enp6s0，用 ip route get 1.1.1.1 查实际网卡。libvirt 自带的 NAT 规则通常已足够，这一步主要保证 VM 能拉镜像。

until kubectl get --raw=/readyz >/dev/null 2>&1; do sleep 5; done; echo apiserver ready
预期：1~3 分钟后输出 apiserver ready。
启动 worker
for v in k8s-node1 k8s-node2 k8s-node3 k8s-node4; do virsh -c qemu:///system start $v; done
kubectl wait --for=condition=Ready node --all --timeout=600s
预期：5 个 condition met。超时 → virsh net-dhcp-leases virbr-k8s 看 VM 是否拿到 .10-.14 的 IP。
等待核心组件就绪
kubectl -n kube-system rollout status ds/cilium --timeout=300s
kubectl -n kube-system rollout status deploy/hubble-relay --timeout=300s
kubectl -n metallb-system rollout status deploy/metallb-controller --timeout=300s
kubectl get pod kafka-controller
kubectl rollout status sts/kafka-broker --timeout=600s
kubectl -n kube-system rollout status ds/vector --timeout=300s
预期：全部 successfully rolled out；kafka-controller 1/1 Running。
kafka-controller 不存在 → Kafka 需重建（第 6.2 节）。
核对 MetalLB 地址未变
kubectl get svc -A | grep LoadBalancer
预期：kafka-0~3-external = 192.168.100.200~203；my-nginx = .204；targets = .210~.214。
若 Kafka 地址变了：重跑 $K/kubeadm-cluster/03-deploy-5nodes.sh，并修改 $N/backend/vigil/bridge.py 中的 KAFKA_BOOTSTRAP。
确认 Kafka 有数据
kubectl exec kafka-broker-0 -- /opt/kafka/bin/kafka-console-consumer.sh \
  --bootstrap-server kafka-svc.default.svc.cluster.local:9092 --topic ebpf-net-logs --max-messages 2 --timeout-ms 20000
预期：2 行 JSON。
重启后端，让 bridge 重新连上 Kafka
systemctl --user restart netsentinel
sleep 20; journalctl --user -u netsentinel --since '-1 min' | grep -E 'AdsMLModel|bridge|drainer'
预期：AdsMLModel loaded、vigil bridge + drainer threads started、bridge starting → bootstrap=...，且没有 bridge error。
（需要时）宿主机 Hubble 观察
nohup kubectl -n kube-system port-forward svc/hubble-relay 4245:4245 > /tmp/hubble-pf.log 2>&1 &
hubble observe --server localhost:4245 --last 5
端到端验证

sleep 15
docker exec pg psql -U vigil vigil -c "select created_at, src_ip, is_attack, attack_type from vigil_detectionrecord order by created_at desc limit 5;"
预期：出现源 IP 为 192.168.100.20~29、刚刚写入的记录；前端 /vigil/log 15 秒内刷新出来。
