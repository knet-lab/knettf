7. 日常管理与变更

读完你能：每天用 2 分钟确认系统健康；管理账号和令牌；改了前端 / 后端 / 模型 / 集群后让它正确生效；知道日志在哪、出问题从哪查起。
本章讲“做什么、为什么”，每一步的预期输出和异常处理见 运维手册 · 运维操作逐步骤。

7.1 每日健康检查（命令行，约 2 分钟）

export N=~/github/NetSentinel K=~/knetsentinel

# ① 服务与端口：两行 active，HTTP 200
systemctl --user is-active netsentinel cloudflared-knettf
curl -s -o /dev/null -w '%{http_code}\n' http://localhost:8080/

# ② 模型加载、bridge 在消费
journalctl --user -u netsentinel --since today | grep -E 'AdsMLModel (loaded|not loaded)' | tail -1
journalctl --user -u netsentinel --since '-10 min' | grep -E 'vigil.bridge|bridge error' | tail -3

# ③ 数据库：最新记录时间、明天的分区存在、轮转日志
docker exec pg psql -U vigil vigil -Atc "select max(created_at) from vigil_detectionrecord;"
docker exec pg psql -U vigil vigil -Atc "select to_regclass('vigil_detectionrecord_'||to_char(now()+interval '1 day','YYYY_MM_DD'));"
tail -1 /tmp/rotate_partitions.log

# ④ 集群：5 VM running、5 节点 Ready、没有异常 Pod
virsh -c qemu:///system list --all
kubectl get nodes
kubectl get pods -A | grep -vE 'Running|Completed'

# ⑤ 磁盘
df -h / /home

判断“检测是否在工作”的顺序：Kafka 有数据吗（kafka-console-consumer --max-messages 2）→ 后端有 bridge 日志吗 → 有 bridge error 吗 → 分区在吗。九成情况是 bridge 线程退出，重启后端即可。

7.2 账号与令牌

cd $N/backend; PY=../.venv/bin/python
操作命令
改密码$PY manage.py changepassword admin
新建超级管理员$PY manage.py createsuperuser
设为管理员$PY manage.py shell -c "from kcore.models import User;u=User.objects.get(username='alice');u.is_staff=True;u.save()"
停用账号同上，u.is_active=False（已发出的 access token 仍有效直到过期，最多 2 小时）
列出所有用户sqlite3 db.sqlite3 "select id,username,email,is_staff,is_active,last_login from kcore_user;"
重新生成服务 token$PY manage.py generate_bridge_token --write-env → systemctl --user restart netsentinel；如部署了入口 B，同步更新 Secret detector-secret 并 rollout
VIGIL_BRIDGE_TOKEN 是 vigil-bridge 用户的 10 年期 JWT：既能调所有需要登录的 REST 接口，又是入口 B 的共享密钥。泄露后立即重新生成。注意：重新生成不会让旧 token 失效（JWT 无状态，只要签名对、没过期就有效），要真正作废需改 SECRET_KEY（会让所有人重新登录）或停用 vigil-bridge 账号。

场景顺序要点详细步骤

7.6 排障思路

按“从外到内”逐层排除，每层用一条命令确认：

浏览器打不开 knettf.com
  ├─ curl localhost:8080 正常？ ── 否 → systemctl --user status netsentinel；journalctl 看启动报错
  │                                      （常见：.venv 坏了、pg 没起、.env 缺 ENVIRONMENT、settings 语法错）
  └─ 是 → cloudflared 问题：systemctl --user status cloudflared-knettf

网页能开，但某个功能报错
  ├─ 浏览器 F12 → Network，看哪个 /api/ 请求失败、状态码、响应里的 message
  ├─ 401 → token 过期且 refresh 也过期 → 重新登录
  ├─ 403 → 不是 owner 也不是管理员
  ├─ 404 → URL 拼错（末尾斜杠？）或对象不存在
  ├─ 500 → journalctl 看 Traceback
  └─ Kubernetes 页全部失败 → 集群没开 / kubeconfig 过期

检测没有新数据
  Kafka 有数据？ → 否：Vector / hubble-relay（kubectl logs）
                → 是：后端有 bridge error？ → 是：Kafka 恢复后重启后端
                                           → 否：有 drainer failed？→ 看后面的异常（多为缺分区）
                                                                → 否：发包源 IP 是否被当成基础设施过滤了？

完整的“现象 → 检查 → 处理”表见 运维手册第 10 节。

7.7 禁止事项

  • 不要在群聊、邮件、截图里暴露 kubeconfig、密码、.env 内容、token。
  • 不要删除 vigil-bridge 账号；不要在生产库上跑 users_clear / autotf_clear。
  • 不要删除 kafka-controller Pod、任何 Namespace，不要强制重启 Cilium、Kafka、MetalLB。
  • 不要同时开启两个检测入口。
  • 不要对不了解的 Terraform 配置执行 Apply。
  • 不要 sudo bash 跑集群脚本；不要 docker stop pg 后忘了启动。
  • 不要在线上服务运行时另起 manage.py runserver（会再启一个 bridge）。
  • 不要删 ~/vm-images/ubuntu-22.04-cloudimg.qcow2（5 台 VM 的基础镜像）。
